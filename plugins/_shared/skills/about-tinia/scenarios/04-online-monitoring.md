# 场景：工厂在线 / 设备 PdM 监测

> Tinia Production 的目标场景（规划中 / 路线图）。**当前不卖**，但要给客户讲清楚"我们后续怎么演进到这里"，避免客户现在就选择竞品做在线监测。

---

## 客户画像

- **类型**：
  - 风电场远程运维方
  - 工业泵 / 电机厂 PdM 团队
  - 燃气轮机 / 大型旋转机械维保团队
  - 制造业产线设备健康监测
- **业务**：传感器实时采集 → 异常检测 → 提前预警 → 减少停机
- **当前工具**：
  - 大多是"传统震动监测 + 简单阈值告警"
  - 一些用 GE Bently Nevada / NI LabView 等
  - 部分自建 Python 在线系统但功能简单

---

## 痛点 vs Tinia Production 解法

| 痛点 | 现有工具 | Tinia Production（规划中）|
|---|---|---|
| 算法太简单（仅阈值告警）| ✅ 跑得动但不智能 | DAG + 心声 + ML 复杂指标 |
| 想加新算法很难 | 厂家定制 / 自己写 | 节点商店订阅 / AI 自研 |
| 多机协同难 | 各机器各自跑 | 一条产线统一调度 |
| 跟 MES / ERP 集成困难 | 各厂家专有接口 | 标准 REST API |
| 模型 / 算法升级麻烦 | 升级要现场重装 | OTA 远程热更新 |
| 工程师不会用 | 学习曲线陡 | AI 工程师助手降低门槛 |

### 关键能力（区别于 Tinia Pro）

| 能力 | 说明 | 当前进度 |
|---|---|---|
| **实时流处理** | 秒级延迟 vs Pro 离线批处理 | 🟡 底座已有：SDK 流式会话 + 三大分析节点无缝逐帧（Pro/Server 可用）；产线化封装在路线图 |
| **多机协同** | 一条产线 5-20 个工位同时跑同一流程定义 | 🔵 规划中 |
| **数据库 / MES 集成** | 分析结果直接进 ERP / MES | 🔵 规划中 |
| **告警 + 推送** | 异常超阈值实时邮件 / 短信 / Webhook | 🔵 规划中 |
| **模型 OTA** | 云端改流程 → 自动推到边缘节点热更新 | 🔵 规划中（平台侧"改参自动生效"已有雏形）|
| **离线 / 在线同源** | 同一份流程定义，离线分析跟在线流处理用同一份 | 🟡 同一执行内核，已具备基础 |

### 跟 Tinia Pro 的关系

- **架构上**：执行始终发生在 tinia-server 进程内（没有第二个引擎；早期设想的 tinia-engine / tinia-runtime 独立化已归档，节点 SDK 统一并入主仓 go:embed）。Production 走的是同一执行内核 + 流式数据流调度的延伸。
- **实时基座已先行落地**：SDK 流式会话（持续推数据 / 实时取结果）+ 声级计 / 频谱 / 倍频程跨窗无缝逐帧 + 常驻执行池（热进程复用）已在 Pro/Server 可用——这正是 Production"边采边算"的底座，Production 主要补"产线集成 / 设备接入 / 告警推送 / 多机调度"那一层。
- **流程定义**：相同结构化定义，离线 / 在线无缝切换
- **节点生态**：相同节点市场，Pro 节点 + 流处理节点
- **客户路径**：Pro 客户可以零迁移升级到 Production
- **学习曲线**：Pro 用户上手 Production 几乎无新学习成本

## 当前 / 过渡方案（现阶段）

### 客户现在想做在线监测怎么办？

#### 方案 A：用 SmartQuality（Bestfunc 现有产品）

- SmartQuality 是 Bestfunc 已有的工业声学在线检测产品线
- 现在已在汽车 NG 检测 / 产线声学一致性等场景上跑
- 客户当前需求大多能满足

#### 方案 B：Pro / Server + 离线分析支撑

- 用 Tinia Pro / Server 做离线分析、训练模型、调参
- 调好的流程导出给现有在线工具用（或者临时拿 Pro 跑批处理）

#### 方案 B+：SDK 通路把平台算法接进现有在线系统（已可用）

> 不必等 Production 就能让"在线系统调用 Tinia 算法"——这是 v1.33+ 已交付的真实能力。

- 管理员生成 SDK 包（凭据 + 地址内置），客户现有在线 / 边缘程序 `import tinia_sdk` 调用平台上调好的分析
- **SDK 流式会话（v1.35）**：持续往流程推传感器数据、实时取回计算结果，适合在线 / 边采边算；实时直调跳过缓存、走内存中转
- **常驻执行池（v1.35）**：分析节点进程常驻待命，高频 / 实时调用复用热进程，省掉每次启动开销
- **SDK 调用分析（v1.35）**：调用量 / 成功率 / 耗时 / 最近失败可观测
- 适合"算力集中在一台 Tinia server、现场程序只管采集 + 调用"的轻量在线架构（区别于 Production 的多机边缘 + MES 集成 + OTA 完整形态）

#### 方案 C：等 Production v1.0（规划中）

- 跟客户提前打招呼："我们后续阶段会出在线版本（规划中），您先用 Pro 把离线流程跑通，到时无缝升级"
- 适合愿意等的、希望长期跟 Tinia 绑定的客户

## 销售场景

### 客户："我们想做风电场在线 CMS"

**1. 不要 oversell Tinia Production 已经能做**

诚实说："Tinia Production 在产品路线图上（规划中）。如果您在后续阶段启动 PoC，正好赶上首批客户。

当前我们能提供：

- 离线分析：用 Tinia Pro / Server 把您历史数据跑通，验证算法 + 训练异常检测模型
- 轻量在线：通过 SDK 流式会话（已交付）让您现场程序持续推数据、实时取回 Tinia 算法结果，先把"算法这一层"在线跑起来
- 在线检测整套：可以先用 SmartQuality（Bestfunc 现有产品）过渡，到时升级到 Production（规划中）
- PoC 阶段：我们派人现场支持，跟您一起设计部署架构"

**2. 给具体路径**

```
第一阶段：Tinia Pro 离线跑通您的算法 + 出 PoC 报告
第二阶段：Tinia Production 设计 → PoC 选型 → 您是首批用户（规划中）
第三阶段：现场部署 + 测试
后续：全产线上线 + 长期维护
```

**3. 商业模型**

- 离线分析阶段：Pro 多 seat
- PoC 阶段：项目咨询费 + 集成开发
- 上线阶段：Production 项目交付（含硬件 / 集成 / 运维）

### 客户："我们工业泵 PdM 想升级"

类似路径：

- 第一阶段：用 Tinia Pro 做离线诊断 + 模型训练
- 后续阶段：Production 上线部署到设备现场（规划中）

## 给 Tinia Pro 客户铺垫"Production 升级路径"

**所有 Pro 客户**销售时都顺带提一句：

> "您今天用的 Pro 版的所有节点 + 流程定义，等 Production 上线后（规划中）能直接搬过去用，不用重写。
>
> 我们的架构就是为'离线 → 在线'演进设计的。"

这给客户**长期信心** + **避免被竞品的"在线方案"挖角**。

## Production 客户的关键差异

跟 Pro 客户对比，Production 客户有几个特殊点：

| 维度 | Pro 客户 | Production 客户 |
|---|---|---|
| 决策周期 | 几周到几个月 | 半年到一年 |
| 决策人 | 工程师 / 主管 | 工厂老板 / 设备总监 |
| 关键关注 | 工程师效率 | 产线 OEE / 故障预防 ROI |
| 部署 | 工程师 PC | 工厂 IT + 边缘硬件 |
| 服务 | 主要技术支持 | 长期运维 + 模型迭代 |
| 商业 | seat 订阅 | 项目交付 + 服务费 |
| 客户成功 | 月度跟进 | 周度甚至日度跟进（关键阶段） |

---

## 风险与缓解（销售要心里有数）

| 风险 | 影响 | 缓解 |
|---|---|---|
| Production 上线晚于预期 | 客户失望 | 销售时给"路线图"而不是"承诺"，过渡方案打底 |
| 客户嫌等不及选竞品 | 流失 | 给离线 Pro 先合作建立关系 + 显示技术深度 |
| 客户算力 / 网络条件不够 | 部署失败 | PoC 阶段先验证基础设施 |
| 模型精度不达标 | 客户不付尾款 | 离线阶段先证明算法可行性，不冒进上线 |

- Production v1.0 上线 → 5-10 个首批客户（规划中）
