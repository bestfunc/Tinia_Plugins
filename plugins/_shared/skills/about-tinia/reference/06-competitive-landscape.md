## 三条不可复制的差异化

### 1. MCP-native 协作 ✅

**为什么对手追不上**：

- HEAD / Testlab 基于桌面单机架构演进多年，进程模型 + UI 架构非为"外部 AI 调用"设计
- 要做 MCP 接入需要重写大量基础设施（HTTP server、auth、事件总线）
- 现有 SDK 只是给"人写代码"用的，不是"AI 自动调用"的
- 即使他们意识到要做，也要 3-5 年重构

**Tinia 的实现**：

- 主仓 `/api/v1/mcp` 端点直接内置 MCP server
- OAuth 2.1 + PKCE + 动态客户端注册（DCR）让 AI 客户端一键授权
- 65+ 个 MCP 工具覆盖项目 CRUD / 文件读写 / 节点脚手架 / 编译 / 跑流程 / 发布
- Claude Code / Codex / Qwen CLI 装上 `Tinia_Plugins` 中的 plugin 即用

详见 `11-mcp-ai-integration.md`。

### 2. 节点 DAG + AI 编排（不是脚本，是声明式图）✅

**为什么对手追不上**：

- 传统工具是"菜单驱动 + 模块化处理"，工程师在菜单里一步步点
- HEAD ArtemiS 16 才加 Automation Project（脚本化向导），本质仍是命令式
- Siemens Process Designer 也是相同形态
- 改成 DAG 需要重做核心数据流模型，不是 UI 改改的事

**Tinia 的实现**：

- 流程是有向无环图（DAG），节点为顶点，数据流向为边
- 执行引擎按拓扑序调度，节点完成后自动把 outputs 通过 blob handle 传给下游
- 这是**声明式**而非**命令式** —— AI 能直接读懂、改、新建
- 工程师说"我要看这段信号的频谱在转速 1000-3000 RPM 段的演化"，AI 能自动搭 DAG

### 3. 开放节点商店（tinia-store）✅

**为什么对手追不上**：

- HEAD / Testlab 的商业模式是"卖大厂自己的软件"，开放商店会侵蚀模块收入
- Ansys / Abaqus 有 user subroutine（自定义代码扩展）但没有"商店"概念
- 真正的"App Store"需要支付 / 分成 / 审批 / 推荐算法的完整基础设施

**Tinia 的实现**：

- `Tinia_Store` 独立服务，独立可部署
- 节点发布审批 + 用户订阅 + 商业节点收费 + 30% 平台分成
- 公开（所有人可订阅）/ 私有组织池（仅组织内可见）两种发布范围
- 2026 H2 内部跑通，2027 对外开放

## 对手强项（Tinia 短期不追的）

要诚实告诉客户 Tinia 现在**还做不到**或**短期不做**的事：

| 对手强项 | Tinia 现状 / 计划 | 给客户的话术 |

| **EMA / 模态分析** | ❌ H2 不做，2027 Q1 评估 | "重型功能，我们暂不做。如果是模态分析为主，HEAD/Testlab 更合适。但 90% NVH 工程师不每天用 EMA" |
| **TPA / 传递路径分析** | ❌ 同上 | 同上 |
| **建筑声学（RT60/STI）** | ❌ 不在核心客户群 | "不是我们的目标场景。建议用专门工具（如 DIRAC）" |
| **Beamforming / 声学相机** | ❌ 需要硬件配合，不做 | "纯软件没法做，建议 B&K / HEAD 整套硬件方案" |
| **30 年算法清单（134 项）** | 33+ 节点 + AI 编排补组合空间 | "我们覆盖核心 60%+ 高频用例，AI 编排让你能从已有节点搭出绝大部分组合。剩下专属的 5% 我们能给你定制节点" |
| **培训生态** | 早期，没有大量教程 | "我们的优势是 AI 工程师助手 + 文档站 + 客户成功跟到底，不靠传统培训" |

## 销售场景：客户对比时怎么应答

### 场景 A：客户说"你们功能没有 HEAD 全"

**❌ 错答**："我们正在追，今年就能有 XX"
**✅ 正答**：

> "您说得对，HEAD 30 年累积的算法清单很全。但请问您日常用到的是哪 10-20 个核心算法？这些 Tinia 都有。HEAD 那些深功能（EMA / TPA / 全套建筑声学），90% 工程师 99% 时间用不到。
>
> Tinia 的差异化不是'算法多少'，是'**工作方式**'：节点 DAG + AI 编排 + 节点商店即时更新。我们一份月度报告，HEAD 用户 2 天，Tinia 用户 2 小时。"

### 场景 B：客户说"你们便宜是因为功能少"

**❌ 错答**："不是不是我们也有 XX 功能"
**✅ 正答**：

> "我们便宜不是因为功能少，是因为架构代际不同。
>
> HEAD 基于桌面单机架构的成熟商业软件 → 边际成本高 → 单 seat 必须贵
> Tinia 云原生 + 订阅 + AI 增效 → 边际成本接近零 → 我们能定低价
>
> 我们功能虽不及 HEAD 累积全，但**该有的核心都有 + AI 工程师助手是 HEAD 5 年内不会有的**。"

### 场景 C：客户说"我们这是大企业，工具要稳定，不敢用新的"

**❌ 错答**："我们也很稳定您放心"
**✅ 正答**：

> "理解您的顾虑。这是 Tinia 的**典型客户决策路径**：
>
> 1. 先试用 Community 或 Pro 试用 3 个月，让 1-2 个工程师在非关键项目里用
> 2. 出了 2-3 个真实案例，证明 Tinia 能做 + 工程师真喜欢
> 3. 再在团队层面铺开
>
> 这是低风险高回报的路径。HEAD 不会从您预算里消失，Tinia 是**新增**而非**替代**。"

### 场景 D：客户问"5 年后你们还在吗？怎么避免被锁死"

**❌ 错答**："放心我们融了很多钱"
**✅ 正答**：

> "三层保障：
>
> 1. **流程 JSON 开放**：您的流程定义就是个 JSON 文件，标准化 schema，无论 Tinia 在不在都能解析
> 2. **节点代码可控**：商业节点您能看到接口、签合同保留源码托管；自研节点完全在您手里
> 3. **核心架构 Apache-2.0**：Tinia engine 是开源的，公司停摆社区也能继续
>
> 我们认为最大的护城河不是 lock-in，是产品好让您不想走。"

## 不直接对比的关键："投资人 vs 客户"叙事

**对客户**：讲"工作方式升级 + 工具效率提升 + 节点商店"
**对投资人**：讲"AI-native 工程操作系统 + 节点商店生态 + 长期取代传统工具"

两边叙事不冲突，但**侧重不同**：

- 客户最关心当下我能省多少时间 / 钱
- 投资人最关心 5 年后 TAM 有多大 / 护城河有多深

不要给客户讲"我们要取代 HEAD"——客户会怕"你倒了我没人用"，**讲"我们补充 HEAD" + "AI 工程师是新的工具范式"**。
